## How it's built

Four modules, and only one of them knows about Spring: the encoder, the validation and the SVG and PNG rendering are plain libraries, and the API is the only layer with a framework. The encoder uses no ready-made library: UTF-8 byte mode, all 40 versions at the 4 correction levels, Reed-Solomon over GF(256) with block interleaving, the 8 masks with their penalties, and format and version info with BCH.

## Decisions worth reading

- **Tested in three layers:** the specification's test vectors, a matrix identical to ZXing's module by module across all 40 versions and 4 levels, and real reading, where the QR becomes an image and the reader returns the original text. ZXing is only used in tests.
- **Logo area by the real math:** how many codewords it destroys in each block versus how many that block can correct. In automatic mode, the correction level rises on its own until the logo fits.
- **Checked with a real camera.** A calibration page with 46 QR codes, from 1.5:1 to 21:1 contrast, showed the phone hesitating around 2.5:1. The limit was set at 4.5:1.
- **The server revalidates on export.** The file only comes out if validation passes, regardless of what the interface showed. If it fails, the response is a 422 with the reasons.

The QR in this site's contact section was generated by this API and went through the same validation. The demo runs on a free server that sleeps, and the editor lets you know while it wakes up.
